## 2. Ce qui marche

Parcours vérifiés de bout en bout :

- `GET /` → page de recherche (200)
- `GET /search?q=aspirine` → 2 spécialités + 2 alternatives, **108 ms**
- `GET /search?q=…&filter=specialty|active` → filtrage correct, **40 ms**

La logique métier est juste : la double recherche marque/substance, le rapprochement par groupe générique BDPM et le repli sur principe actif produisent les bons résultats.

## 3. Défauts bloquants (P0)

### P0-1 — Requête N+1 : auto-déni de service

`src/search.js:116` lance **une requête SQL par résultat** pour chercher les génériques.

Mesures réelles (base de 3 000 lignes) :

| Requête | Requêtes SQL | Temps | Poids HTML |
|---|---|---|---|
| `aspirine` | 4 | 43 ms | 8 Ko |
| `me` | **3 004** | 1 692 ms | 545 Ko |
| `a` | **6 010** | 2 910 ms | 1,1 Mo |

Aucune limite serveur sur la longueur de la requête ni sur le nombre de résultats. La BDPM réelle compte ~16 000 CIS : une recherche sur `e` déclencherait ~32 000 allers-retours SQL sur un pool de 10 connexions, en série. Le serveur est monothread → **blocage complet du processus**.

Aggravant : l'autocomplétion appelle ce même endpoint `/search` toutes les 300 ms de frappe, avec tout le calcul des produits liés, pour n'afficher que 5 suggestions.

**Correctif :** remplacer la boucle par une requête unique `WHERE cg1.code_cis = ANY($1)`, plafonner à `LIMIT 50` côté serveur, imposer 3 caractères minimum côté serveur, et créer un endpoint `/api/suggest` léger (marque uniquement, `LIMIT 8`, pas de produits liés).

### P0-2 — XSS stocké + redirection ouverte

Trois vecteurs vérifiés en injectant un document piégé en base :

1. `views/product.pug:102,119,136` — `!= doc.html_content` injecte le HTML brut. Test : `<script>alert(1)</script>` **remonte intact dans la page produit**.
2. `index.js:266` — `/api/document/:cis/:type` sert le HTML brut avec `Content-Type: text/html` sur la même origine → XSS stocké exploitable directement.
3. `index.js:260` — `res.redirect(document.file_path)` sans validation. Test : redirection **302 vers `https://evil.example.com`** obtenue.

Le contenu vient du scraping ANSM, donc d'une source externe non maîtrisée. Sur une application santé, c'est éliminatoire.

**Correctif :** assainir le HTML (`sanitize-html`, liste blanche de balises) à l'insertion **et** au rendu ; servir les documents dans une iframe `sandbox` ou avec une CSP stricte ; valider que `file_path` pointe vers un domaine autorisé (`ansm.sante.fr`, `base-donnees-publique.medicaments.gouv.fr`) avant redirection.

### P0-3 — Configuration en dur, aucun secret externalisé

`index.js:42-47` et `src/__tests__/search.test.js:9-14` :

```js
const pool = new Pool({ user: 'laurentstaub4', host: 'localhost',
                        database: 'incidents_json', port: 5432 });
```

Identifiants, hôte, base, port et `PORT = 3000` sont figés dans le code, dupliqués dans les tests. Pas de `.env`, pas de `dotenv`, aucune variable d'environnement lue. Le projet ne peut tourner que sur ta machine, sous ton compte.

**Correctif :** un module `config.js` unique lisant `process.env` (`DATABASE_URL`, `PORT`), `.env` dans `.gitignore`, `.env.example` commité.

## 4. Défauts sérieux (P1)

### P1-1 — Deux tests rouges par construction

```
Tests: 2 failed, 5 passed, 7 total
```

Ce ne sont pas des régressions, c'est une contradiction de conception : les tests affirment que **tous** les résultats contiennent le terme cherché, alors que `relatedProducts` retourne par définition des produits *différents* (génériques, alternatives). Le test `aspirine 500` échoue sur `ASPIRINE PROTECT 100 mg`, correctement retourné comme alternative.

Aggravant : ce sont des tests d'intégration exigeant une base locale peuplée de données réelles (ASPIRINE, OZEMPIC). Ils sont ininstallables en CI et se cassent à chaque mise à jour BDPM.

**Correctif :** assertions par catégorie (`brandMatches` doit contenir le terme, `relatedProducts` non) ; extraire la construction des clauses SQL en fonctions pures testables sans base ; réserver 2-3 tests d'intégration à un jeu de données figé (fixtures SQL versionnées).

### P1-2 — Erreurs 500 sur entrées malformées

| Entrée | Résultat | Cause |
|---|---|---|
| `/product/abc` | **500** + trace SQL en console | `index.js:131` — `($1)::numeric` sur `'abc'`, erreur PG `22P02` |
| `/search?q=a&q=b` | 500 (`query.trim is not a function`) | `search.js:12` — Express renvoie un tableau |

Aucune validation d'entrée, aucun middleware d'erreur, aucun handler 404 applicatif.

**Correctif :** valider `:id` par `/^\d+$/` → 404 ; normaliser `req.query.q` (`Array.isArray ? q[0] : q`) ; ajouter un middleware d'erreur terminal et un 404 catch-all.

### P1-3 — `/api/data` : exposition intégrale de la base

`index.js:316` — `SELECT * FROM dbpm.cis_bdpm` sans pagination ni limite, servi avec `Access-Control-Allow-Origin: *` (vérifié). 428 Ko sur 3 000 lignes de test → plusieurs Mo sur la BDPM réelle, à chaque appel, depuis n'importe quel domaine.

**Correctif :** supprimer l'endpoint (il ne sert aucune vue) ou le paginer et restreindre le CORS à l'origine du front.

### P1-4 — Logique dupliquée entre `search.js` et `index.js`

Le calcul des produits liés existe **deux fois**, dans deux implémentations divergentes :

| | `src/search.js:105-188` | `index.js:155-221` |
|---|---|---|
| Limite alternatives | 30 puis 50 | 15 |
| `type_generique` remonté | non | oui |
| Tri princeps/générique | non | oui |

Toute évolution devra être faite aux deux endroits — c'est déjà en train de diverger.

**Correctif :** extraire `src/products.js` avec `getRelatedProducts(pool, cisCode)`, appelé par les deux routes.

## 6. Performance SQL

Les clauses de recherche sont de la forme :

```sql
unaccent(LOWER(m.denomination_medicament)) LIKE unaccent('%aspirine%')
```

Double problème : **fonction appliquée à la colonne** (aucun index B-tree utilisable) et **joker en tête** (aucun index de préfixe utilisable). Chaque recherche est un *seq scan* complet de `cis_bdpm` **et** `cis_compo_bdpm`, multiplié par le N+1 du P0-1.

**Correctif :**

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_cis_denom_trgm ON dbpm.cis_bdpm
  USING gin (unaccent(lower(denomination_medicament)) gin_trgm_ops);
CREATE INDEX idx_compo_subst_trgm ON dbpm.cis_compo_bdpm
  USING gin (unaccent(lower(denomination_substance)) gin_trgm_ops);
```

(`unaccent` doit être rendue `IMMUTABLE` via un wrapper pour être indexable.)

## 8. Question de fond

Le localisateur de pharmacies, les stocks et les interactions ont été ajoutés puis retirés entre juillet et octobre 2025 (`74de104` → `912aadf`), en laissant leurs traces dans le CSS et le README. Ce qui reste est un **moteur de recherche BDPM enrichi des ruptures d'approvisionnement** — et c'est précisément ce qui n'existe pas correctement ailleurs.

Avant de reprendre le code, vaut-il mieux trancher le périmètre : « recherche médicament + disponibilité temps réel », un point c'est tout ? Le nettoyage devient alors une suppression franche plutôt qu'un arbitrage ligne à ligne.
